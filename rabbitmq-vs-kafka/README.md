# RabbitMQ와 Kafka의 차이 시뮬레이터

AWS 비교 문서의 차이점을 "움직이는 그림"으로 보여 주는 시뮬레이터예요. 가상 데이터만 쓰고, 실제 브로커나 서비스에는 연결하지 않아요.

- 주소(배포 뒤): `https://jung-min-ju.github.io/notification-sim/rabbitmq-vs-kafka/`
- 삽입 모드: `?embed&s=<상황>` (상황: `consume`, `fail`, `multi`, `order`, `priority`, `route`, `thru`)

## 근거

- 문서: [Kafka와 RabbitMQ의 차이점은 무엇인가요? (AWS)](https://aws.amazon.com/ko/compare/the-difference-between-rabbitmq-and-kafka/)
- 확인일: 2026-10-27 (문서 메타데이터의 갱신 시각: 2026-08-07)
- 이 문서에는 코드 사실(파일·메서드·쿼리)과 실측값이 없어요. 성능 수치는 문서의 정성적 표현("초당 수천 건", "초당 최대 수백만 건")뿐이에요.

- 소비자 장애·소비자 여러 명·순서 장면은 AWS 문서가 아니라 아래 공식 문서와, 팀이 붙여 준 정리글을 근거로 해요. 확인일 모두 2026-10-27.
  - [RabbitMQ Consumer Acknowledgements and Publisher Confirms](https://www.rabbitmq.com/docs/confirms): ACK 전에 채널·연결이 닫히면 메시지가 큐에 되돌아가고(redelivered), 가능하면 원래 위치로, 아니면 앞쪽으로 들어가요. 다른 소비자가 받을 수도 있어요.
  - [RabbitMQ Consumers](https://www.rabbitmq.com/docs/consumers): 큐의 활성 소비자에게 메시지를 기본적으로 번갈아(라운드 로빈) 보내요.
  - [Apache Kafka 소개](https://kafka.apache.org/intro/): 소비해도 이벤트를 지우지 않고, 소비자는 몇 명이든 필요한 만큼 읽을 수 있어요. 순서는 파티션 안에서만 보장하고, 같은 키는 같은 파티션으로 가요.
  - [KafkaConsumer javadoc (3.1)](https://kafka.apache.org/31/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html): 커밋한 위치는 안전하게 저장된 마지막 오프셋이고, 장애 뒤에는 그 위치에서 이어 읽어요. 소비자 그룹마다 토픽을 독립적으로 읽고, 한 그룹 안에서는 파티션 하나를 소비자 한 명에게만 줘요. 처리했지만 커밋하지 못한 레코드는 다시 읽힐 수 있어요(at-least-once).
  - 문서에서 직접 확인하지 못한 것: RabbitMQ의 "큐 하나·소비자 한 명이면 보낸 순서대로 전달"은 정리글의 설명을 따랐어요. 위 문서들에서 문구로 확인하지 못했어요.

## 문서에서 가져온 차이

| 항목 | RabbitMQ | Kafka |
| --- | --- | --- |
| 소비 방식 | 브로커가 소비자에게 밀어 줌(push) | 소비자가 오프셋을 기억하며 가져감(pull) |
| 소비한 메시지 | ACK를 받으면 큐에서 삭제 | 보존 기간까지 로그에 남음, 다시 처리 가능 |
| 우선순위 | 우선순위 큐로 특정 메시지를 먼저 처리 | 우선순위 큐 없음, 모든 메시지를 동등하게 취급 |
| 라우팅 | 거래소가 라우팅 키로 큐를 정함 | 메시지 키로 토픽의 파티션이 정해짐 |
| 처리량 | 평균 초당 수천 건, 큐가 혼잡하면 느려질 수 있음 | 순차 디스크 I/O로 초당 최대 수백만 건 |
| 생산자가 아는 것 | 메시지가 소비자에게 도착했는지 모니터링 | 소비자가 가져갔는지 알지 못함 |

## 상황 표

| 상황 | RabbitMQ | Kafka | 성격 |
| --- | --- | --- | --- |
| 소비 후 (`consume`) | ACK 뒤 큐에서 삭제, 다시 읽을 메시지 없음 | 로그에 남고 오프셋만 이동, 처음부터 다시 읽기 가능 | 기능 차이 |
| 우선순위 (`priority`) | 긴급 메시지가 앞줄로 들어감 | 도착한 순서대로 읽어서 맨 뒤에서 기다림 | 우선순위 트레이드오프 |
| 라우팅 (`route`) | 거래소가 라우팅 키로 큐 3개에 나눠 담음 | 메시지 키로 파티션 3개에 나눠 저장, 소비자 3개가 가져감 | 구조 차이 |
| 처리량 (`thru`) | 들어오는 속도를 못 따라가 큐에 쌓임 | 들어오는 속도를 따라감 | 규모 대응 |
| 소비자 장애 (`fail`) | ACK 없이 끊기면 그 메시지가 큐로 되돌아가 다시 처리 | 마지막 커밋 위치부터 다시 읽어, 커밋 전에 처리한 메시지가 두 번 처리됨 | 장애 복구 차이 |
| 소비자 여러 명 (`multi`) | 한 큐의 메시지를 소비자 3명이 번갈아 나눠 받음 | 서로 다른 그룹 2개가 모든 메시지를 각자 읽음 | 구조 차이 |
| 순서 (`order`) | 큐 하나에서 보낸 순서대로 처리 | 파티션 2개: 파티션 안은 순서 유지, 파티션 사이는 섞임 | 순서 보장 범위 |

## 시뮬레이션 가정

문서에 없는 값은 화면에 적지 않고 여기에만 적어요. 구현 전 모델 예상이 아니라 문서 설명을 그림으로 옮긴 것이고, 실측이 아니에요.

- 시간은 모델 시간(초)이고 화면에서 1초는 실제 1초예요. 장면이 끝나면 2.5초 멈춘 뒤 처음부터 반복해요.
- 소비자 한 번의 주기: 가져오기 0.35초 + 처리 0.65초 + 사이 간격 0.25초. 두 구조에 똑같이 적용해서 차이가 구조에서만 나오게 했어요. 처리량 상황만 아래 값을 써요.
- 처리량 상황: 점 1개 = 메시지 2,000건, 들어오는 속도 초당 5,000건(점 0.4초당 1개). RabbitMQ 처리 속도는 문서의 "수천 건" 범위 안에서 초당 3,000건으로, Kafka는 들어오는 속도보다 빠른 값으로 정했어요. 큐가 혼잡할 때 느려지는 효과는 모델에 넣지 않았어요.
- 소비 후: 메시지 8건. 다시 읽기는 마지막 처리 1.5초 뒤에 시작해요. RabbitMQ의 다시 읽기는 "큐가 비어 읽을 메시지가 없음"까지만 보여 주고, 생산자가 다시 보내는 과정은 그리지 않았어요.
- 우선순위: 일반 메시지 6건이 큐에 있는 상태에서 1.4초에 긴급 메시지 1건이 들어와요. RabbitMQ는 처리 중인 메시지 다음 순서로 끼워 넣어요.
- 라우팅: 메시지 9건(주문·결제·알림 각 3건). 같은 키는 같은 파티션으로 가요. 소비자 3개가 파티션 1개씩 읽는 구성은 문서에 없는 가정이에요.
- ACK 표시(소비 후·우선순위·소비자 장애): 소비자가 처리하는 동안 큐에 점선 원(ACK 대기)을 남기고, ACK를 받으면 초록 화살표·초록 점이 소비자에서 큐로 약 1초 동안 가고 "삭제" 글자가 잠깐 떠요. 1초는 보기 좋게 정한 값이에요.
- 소비자 장애: 메시지 6건, 4번 메시지를 처리하다 4.8초에 소비자가 끊기고 7.3초에 돌아와 7.6초부터 다시 처리해요. 끊김·복구 시각은 가정이에요. Kafka의 커밋은 "메시지 2건 처리 뒤 커밋"으로 가정했어요(커밋 주기는 공식 문서에 값이 없어요). 그래서 3번 메시지는 처리했지만 커밋 전이라 다시 처리돼요. RabbitMQ는 되돌아간 메시지를 큐 맨 앞에 두고 같은 소비자가 다시 받는 것으로 그렸어요.
- 소비자 여러 명: 메시지 6건. RabbitMQ는 소비자 3명에게 번갈아 가요. Kafka는 그룹 A가 0.4초, 그룹 B가 1.0초에 읽기 시작해요(시작 시각은 가정). 두 소비자는 서로 다른 그룹이고, 같은 그룹이면 파티션 하나를 한 명만 읽어요.
- 순서: 메시지 8건, 0.5초 간격으로 보내고 홀수 번호는 파티션 0, 짝수 번호는 파티션 1로 가요(키로 나뉜다고 가정). Kafka 소비자는 파티션 0의 두 건, 파티션 1의 두 건 순으로 번갈아 가져가요(묶음 크기 2는 가정).
- RabbitMQ는 소비자가 처리 중인 동안 큐에 점선 원(ACK 대기)을 남겨요. ACK를 받으면 점선 원이 사라지고 큐 숫자가 줄어요.

## 시간표 읽는 법

- 가로축은 모델 시간(초)이고, 움직이는 세로 실선이 현재 시각이에요.
- 막대는 소비자가 메시지를 가져와 처리한 구간(가져오기 0.35초 + 처리 0.65초)이에요.
- 빨간 점선 상자는 기다린 구간이에요. 그림에서 같은 점에 빨간 점선 고리가 생기고, 상자가 자라는 동안 "3.0초째 기다리는 중"이 올라가요. 끝나면 "5.9초 기다림"이 남아요.
- 기다림 상자는 우선순위의 긴급 메시지, 처리량의 마지막 메시지, 소비 후의 RabbitMQ 다시 읽기에만 그려요. 0.25초 이하의 기다림은 그리지 않아요.
