# 알림 큐 구조 비교 시뮬레이터

오전 8시에 몰리는 알림 작업(인앱 알림 생성 → DB 저장 → 푸시 발송)을 큐가 어떻게 받고 소비자가 어떻게 가져가는지 움직이는 그림으로 보여 준다. 가상 데이터만 쓰고 실제 서비스나 알림에는 연결하지 않는다.

- 주소(삽입 모드): `?embed&s=burst` / `?embed&s=consume` / `?embed&s=part`
- 파일: `index.html` 한 개. 외부 라이브러리 없이 canvas로 그린다. 글꼴만 Google Fonts에서 불러온다.

## 현재 구조 (코드 사실)

작성일 2026-10-28. **저장소를 아직 확인하지 못했다.** 발송 작업 생성, DB 저장, 푸시 발송 메서드와 쿼리는 확인 후 이 절에 적는다.

## 상황

| 상황 | 비교 대상 | 성격 |
|---|---|---|
| 8시에 몰림 (`burst`) | 큐 없이 바로 처리 / 큐에 저장하고 처리 | 규모 대응 |
| 저장 방식 비교 (`consume`) | Kafka 로그(읽어도 남음) / RabbitMQ 일반 큐(ack하면 지움) | 우선순위 트레이드오프 |
| 파티션 병렬 처리 (`part`) | 파티션 1개 + 소비자 1개 / 파티션 4개 + 소비자 4개 | 규모 대응 |

`consume`에서 Kafka와 RabbitMQ의 처리 시간은 같다. Pull과 Push는 소비 속도를 조절하는 방식일 뿐 처리 시간을 바꾸지 않으므로, 이 상황은 저장 방식(보존 vs 삭제)의 차이만 보여 준다. Pull만으로 Kafka가 더 적합하다고 보지 않는다.

## 실측표

| 항목 | 값 | 출처 |
|---|---|---|
| 푸시 발송 처리량 | 32,000건 / 453.788초 ≈ 초당 70.5건 | #192 실측 (격리 MySQL, 외부 푸시 250ms 대역, 동시 20) |

이 값을 소비자 1개의 처리량으로 쓴다.

## 측정 범위 밖

- Kafka와 RabbitMQ의 저장·읽기 처리량
- 배치·압축·순차 쓰기·페이지 캐시 효과
- 사용자 10만 명 기준 목표 시간 안 완료 여부 (실제 검증 예정)
- 브로커 장애, 소비자 재시작, 재전달

## 시뮬레이션 가정

아래 값은 실측이 아니다. 실측이 생기면 교체한다.

- 작업 10만 건 (사용자 10만 명 × 1건)
- 8시 0분부터 120초 동안 같은 속도로 도착 (초당 약 833건)
- 소비자 1개 = 초당 70.5건 (#192의 푸시 발송 실측을 소비 처리 속도로 가정). 소비자를 늘리면 처리량이 소비자 수에 비례한다고 가정
- 점 1개 = 작업 1,000건. 한 점의 처리 시간 = 1,000 / 70.5 ≈ 14.2초
- 상자 사이 이동 10초 (그림용 값)
- `burst`의 "큐 없이 바로 처리"는 가상 비교. 처리 칸이 찬 동안 들어온 작업은 받지 못한다고 가정
- prefetch 20은 임의값. 쥔 작업 수는 그림 아래 숫자로 표시
- 파티션 4개 = 사용자 4명 단위로 나뉜다고 가정. 같은 색은 같은 파티션
- 재생 속도 기본 15배(느리게 8배, 빠르게 30배). 완료 시각은 도착·처리 모델에서 계산한 값
- `consume`: 보관 기간 안에는 로그가 지워지지 않는다고 가정. Kafka는 소비자가 읽은 뒤에도 기록이 남고, RabbitMQ 일반 큐는 처리 확인 뒤 지운다. 재처리(offset 되돌리기) 동작은 그림으로 그리지 않고 설명문에만 적었다
- 모든 수치는 구현 전 모델 예상

## 삽입

```html
<iframe src="https://jung-min-ju.github.io/notification-sim/queue-consume/?embed&s=burst&v=1" width="100%" height="1180" frameborder="0" scrolling="auto"></iframe>
```

화면 배치는 폭에 따라 바뀐다. 980px 이상은 왼쪽 설명 · 가운데 그림 · 오른쪽 진행 설명(노트북 비율 16:10), 640~979px은 그림 + 옆 설명, 그보다 좁으면 위아래로 쌓는다.

높이는 시각 0, 200, 380, 480, 1480초의 최대 높이를 잰 값이다 (Chromium, 대체 글꼴 기준).

| 상황 | 360px | 720px | 1280px (노트북 비율 프레임 785) |
|---|---|---|---|
| `burst` | 1,154 | 646 | 882 (페이지 전체) |
| `consume` | 1,164 | 658 | 882 |
| `part` | 1,150 | 669 | 882 |

iframe 높이는 휴대폰에서 잘리지 않도록 1,180으로 두고, 블로그 본문 폭(720px)만 쓴다면 680으로 줄일 수 있다. `consume`, `part`는 주소의 `s=`만 바꾼다. 삽입 모드는 720px에서 그림 + 옆 설명 2열이라 16:10을 쓰지 못한다. 16:10은 980px 이상에서만 맞는다.
