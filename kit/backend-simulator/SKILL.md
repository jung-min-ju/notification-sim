# 백엔드 시뮬레이터 만들기

코드와 실측을 근거로, 백엔드에서 무엇이 어디로 움직이는지 보여 주는 한 장짜리 시뮬레이터(index.html + README.md)를 만든다.
정적인 화면은 만들지 않는다. 모든 종류에서 점이 움직여야 한다.

## 도구 파일

규칙 문서, 뼈대, 검사 스크립트는 저장소에 있다. 작업 전에 받는다.

```
git clone --depth 1 https://github.com/jung-min-ju/notification-sim
cd notification-sim/kit/backend-simulator
```

아래 경로는 모두 이 폴더 기준이다. 새 시뮬레이터는 저장소 루트에 상황 폴더(예: `retry-delay-192/`)를 만들어 둔다.

## 먼저 읽을 것

- `references/common.md`: 모든 종류에 쓰는 화면·움직임·글·색 규칙과 CONFIG 형식
- `references/types/<종류>.md`: 고른 종류의 규칙
- `references/dont-do.md`: 사용자가 싫어한 것과 대신 할 것

## 순서

각 단계 끝에 "확인받기"가 있으면, 사용자가 답하기 전에 다음 단계로 넘어가지 않는다.

1. **종류 고르기.** 요청을 보고 하나를 고른다. 한 줄로 확인받는다.
   | 요청 | 종류 | 파일 |
   |---|---|---|
   | "어떻게 생겼어", "전체 구조" | ① 구조 지도 | `types/map.md` |
   | "어떻게 흘러가", "이 기능은 어디를 거쳐" | ② 흐름 추적 | `types/flow.md` |
   | "어디서 터질까", "이러면 문제 없어?" | ③ 문제 예측 | `types/risk.md` |
   | "바꾸면 얼마나 나아져", 실측이 있는 비교 | ④ 개선 비교 | `types/compare.md` |
   애매하면 두 후보와 차이를 한 줄씩 적어 묻는다.

2. **근거 확인.** 저장소·브랜치·커밋 해시, `파일:줄`, 쿼리, 설정값(`application.yml`), 실측(이슈 번호·조건)을 모은다. 확인한 날짜를 붙인다. 코드에서 확인 못 한 것은 "확인 못 함"으로 둔다. 추측으로 채우지 않는다.

3. **명세 채우기.** `templates/spec-<종류>.md`를 복사해 채운다. 채운 명세를 채팅으로 보여 주고 **확인받기**.
   - 두 구조(또는 평소/문제 조건)의 차이가 드러나지 않는 상황은 명세에서 뺀다.
   - 숫자마다 출처(실측 이슈 / 코드 / 가정)를 적는다.

4. **모델.** 시각 계산을 먼저 하고, 그림은 그 결과를 따라가게 한다.
   - ①②: 단계 목록 → 시각. 실측이 없으면 순서만 쓴다(초 단위 숫자 없음).
   - ③④: 칸(슬롯) 기반 이산 사건 모델로 작업마다 시작·끝·결과를 미리 계산한다. ④는 실측 처리 시간에 맞추고, ③은 명세의 가정 조건으로 계산한다.

5. **만들기.** `templates/index.html`을 상황 폴더에 복사하고 `CONFIG START`~`CONFIG END` 사이만 채운다. 엔진은 고치지 않는다. 엔진으로 못 그리는 것이 있으면 고치기 전에 무엇이 필요한지 사용자에게 말한다.

6. **검사.** `node scripts/check.js <폴더>/index.html <출력 폴더>`를 돌린다. 실패가 0이 될 때까지 고친다. 실패가 남은 채로 보고하지 않는다.

7. **미리보기.** 출력 폴더의 `shots/`에서 상황마다 단계 스크린샷을 직접 본다. 겹침, 잘림, 이름 없는 상자, 갑자기 생기는 점이 없는지 본다. 대표 스크린샷을 보여 주고 **확인받기**.

8. **README.** `templates/README.md` 형식으로 쓴다. 코드 사실, 실측표, 실험 조건, 시뮬레이션 가정, 코드 상자의 기준 커밋, 검사 결과의 iframe 높이.

9. **배포.** 사용자가 요청할 때만 커밋·PR을 만든다. 커밋 메시지는 한국어로 쓰고 Claude 관련 문구를 넣지 않는다.

10. **보고.** 짧게 세 가지만: 바뀐 것, 직접 확인한 것, 확인 못 한 것(예: 실제 휴대폰).

## 고쳐 달라는 말을 받았을 때

- 여러 번 나눠 고치지 않는다. 받은 수정을 모아 한 번에 반영하고 검사를 다시 돌린다.
- 같은 종류의 수정을 두 번째로 받으면, 고친 뒤 "이걸 규칙으로 넣을까?"라고 묻는다. 동의하면 `references/`의 해당 파일이나 `scripts/check.js`에 날짜와 이유를 붙여 넣는다.
- 묻기만 한 말에는 고치지 않고 답만 한다.

## 하지 않는 것

- 실제 서비스를 바꾸거나 실제 알림을 보내지 않는다. 가상 데이터만 쓴다.
- 화면에 조건과 가정을 적지 않는다(③의 `예측 · 실측 전` 이름표만 예외). 조건과 가정은 README에 적는다.
- "#9" 같은 기호를 작업 이름으로 쓰지 않는다. "발송 작업 생성", "재시도 대기"처럼 한국어로 쓴다.
- 외부 라이브러리를 쓰지 않는다. canvas와 SVG만 쓴다(글꼴만 Google Fonts).
