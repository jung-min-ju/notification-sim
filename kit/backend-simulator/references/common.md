# 공통 규칙

네 종류(구조 지도, 흐름 추적, 문제 예측, 개선 비교)에 모두 적용한다. 종류별 차이는 `types/`에 있다.

뼈대는 두 가지다(2026-11-19).

| 뼈대 | 파일 | 요점 | 화면 규칙 |
|---|---|---|---|
| 단계형 | `templates/index-step.html` | **무엇이 어떤 순서로 바뀌나** | `step.md` |
| 시간형 | `templates/index-time.html` | **몇 건이 쌓이고 몇 초 기다리나** | 이 파일 2절, 9절 |

뼈대는 종류가 아니라 이 요점으로 고른다(2026-11-19).

| 종류 | 보통 | 예 |
|---|---|---|
| ① 구조 지도 | 단계형 | — |
| ② 흐름 추적 | 단계형 | 쌓이는 양이 요점이면 시간형 |
| ③ 문제 예측 | **문제에 따라 둘 다** | 요청이 몰려 대기열이 쌓임 → 시간형 / 점유가 끝난 작업을 다른 워커가 가져가고 늦은 결과가 버려짐 → 단계형 |
| ④ 개선 비교 | 시간형 | 바뀐 순서가 요점이면 단계형 |

명세에 고른 뼈대와 이유(어느 요점인지)를 한 줄 적는다.
이 규칙은 다먹자 알림 작업(2026-10~11)에서 정한 것을 일반화한 것이다.

## 1. 목표

- 단순한 상자, 흘러가는 점, 숫자 몇 개로 보여 준다.
- 무엇이 어디로 움직이는지 눈으로 보여야 한다. 숫자만 올라가는 그림은 실패다.
- 글로 가득한 화면, 멈춰 있는 화면, 대시보드 같은 화면은 만들지 않는다.

## 2. 화면 구성 (시간형)

단계형 화면은 `step.md`를 본다.

위에서부터: 상황 탭 → 재생 줄(재생/처음부터, 범례 한 줄, 시계) → **16:10 한 화면**.

**노트북 화면 전용이다(2026-11-19).** 휴대폰 폭은 대상이 아니다. 그림 폭은 600px(삽입 모드 최대 폭)이 가장 작고, 그보다 좁은 화면에서는 줄이지 않고 가로로 넘친다. 16:10을 지키면서 폭 360까지 줄이면 그림 높이가 약 135px이 되어 글자를 읽을 수 없기 때문이다.

16:10 한 화면은 위 70%가 그림(시간표 포함), 아래 30%가 설명 영역이다(2026-11-19 코드 상자를 빼면서 다시 70 : 30. 2026-11-02~11-19는 60 : 40).
뼈대(`templates/index-time.html`)가 이 비율과 아래 줄이는 규칙을 이미 지킨다. CONFIG만 채운다.

### 그림 (논리 크기 800 × 350)

- 패널 영역은 y 0~208이다. 두 패널이면 각 392 폭(왼쪽 x 0, 오른쪽 x 408), 한 패널이면 800 폭이다.
- 패널 맨 위에 구조 이름(y 15)과 상태 문구 한 줄(y 31)이 있다. 상자 이름은 y 50 아래에서 시작한다.
- 상태 문구는 문제면 빨강(`bad`), 정상이면 초록(`ok`), 평소면 회색(`neu`)이다. 예: "08:03 재시작 뒤 아무도 안 보냄 · 남은 작업은 정오에 만료".
- 상자마다 무엇인지 이름을 붙인다. 예: "실행기에 한꺼번에 넣은 작업", "DB에서 꺼낼 작업", "서버 · 보내는 중 (20칸)", "외부 푸시", "재시도할 작업".
- 상자 아래에는 숫자를 하나만 둔다. 예: "21,600건 남음", "10,400건 보냄".
- 범례는 재생 줄에 한 줄로 쓴다. 예: "● 점 1개 = 발송 작업 200건".
- 선은 직접 경로를 잡는다(`edges.pts`). 선이 상자나 글자를 지나가면 안 된다. 점은 상자 사이를 선 경로를 따라 움직인다.
- 화면에는 조건과 가정을 적지 않는다. README로 보낸다.

### 시간표 (y 214~350)

- 패널마다 줄을 둔다. 예: "발송", "재시도". 축은 초 단위면 1분 간격, 순서만 있으면 단계 이름이다.
- 기준 시각은 점선 세로선과 위쪽 이름표로 표시한다(`marks`). 예: "재시도할 시각 08:05".
- 기다린 구간은 빨간 점선 상자에 "154초 기다림"처럼 적는다(`waits`). 상자 폭이 70보다 좁으면 안에 쓰지 않고 옆에 "1초 뒤 시작"으로 쓴다.
- 현재 시각 세로선이 움직이고, 그 시각까지만 막대를 드러낸다.
- 곡선이나 막대는 끝에서 0으로 떨어지지 않는다. 축은 두 구조에 같게 두고, 시작 시점도 같게 둔다.
- 그래프가 이해되지 않으면 곡선 대신 막대를 쓴다.

### 설명 영역

- 같은 폭의 카드 두 개다. 왼쪽은 연한 주황, 오른쪽은 연한 파랑이다.
- 머리띠는 작은 색 점과 색 글자로 쓴다. 선 있는 표, 원색 머리띠, 회색 바탕은 쓰지 않는다. 머리띠 이름은 종류마다 다르다(`types/`).
- 카드마다 ① 시작 ② 진행 ③ 끝 세 단계를 흐름 순서로 쓴다. 같은 번호끼리 나란히 둔다. 단계는 세로선으로 잇는다.
  - 지난 단계: 채운 원
  - 지금 단계: 고리를 두른 원, 굵은 글자
  - 남은 단계: 빈 원, 흐린 글자
- 단계마다 본문 한 줄(해요체, 28자 안팎)과 풀이 한 줄(30자 안팎)을 쓴다.
  - 본문: 무엇이 움직이는지
  - 풀이: 왜 다른지, 쓰인 용어(Pull, Push, prefetch, 파티션, 소비자 그룹, 오프셋, 트랜잭션, 선점 등)의 뜻
- **코드는 화면에 두지 않는다**(2026-11-19, 이전 2026-11-10 코드 상자 규칙은 없앰). 코드 상자는 자리를 많이 차지하고, 줄 번호가 금방 낡고, 설계 단계에는 넣을 코드가 없다. 대신 단계마다 근거 `파일:줄`을 CONFIG의 `src`에 적고, README의 "근거 코드"에 커밋과 함께 옮겨 적는다.
- 단계는 목차다. 누르면 그림과 시간표가 그 단계의 시각으로 이동하고 계속 재생한다. Enter와 Space로도 눌린다.
- 설명 영역에도 조건과 가정은 적지 않는다.

## 3. 움직임

- 점은 갑자기 생기거나 사라지지 않는다. 처음부터 출발 상자에 있거나, 다른 점에서 갈라져 나온다.
- 실패한 점은 노란색으로 바뀌어 "재시도할 작업" 상자로 이동하고, 남은 시간을 센다(`notes`).
- 막힌 상황은 그림으로 표시한다. 예: 재시도 상자 옆 빨간 막대와 "못 들어감"(`blocks`).
- 서버 재시작은 상자를 빨간 덮개로 덮고 "서버 재시작"이라고 적는다(`cover`). 끊긴 작업은 ✕로 표시한다(`cut`).
- 칸(슬롯)은 진행 링으로 남은 처리 시간을 보여 준다.
- 다 보낸 점은 받는 상자(`sink`)에 들어가며 흐려진다.

## 4. 글

- 시뮬레이터 안 문장은 붙일 곳의 말투에 맞춘다. 블로그는 해요체다.
- 용어 풀이는 단계의 풀이 줄에 짧게 쓴다. 대화체("~야")와 긴 설명을 피한다.
- "도입 시 사용"처럼 애매한 표현은 쓰지 않는다. 채택한 것은 채택했다고 쓴다.
- 처리 속도, 지연 시간 같은 숫자는 실측에서 가져오고, 출처(이슈 번호)를 README에 적는다.
- 작업 이름은 한국어로 쓴다. "#9" 같은 기호를 쓰지 않는다.

## 5. 색·글꼴

- 글꼴: IBM Plex Sans KR(본문), IBM Plex Mono(시계·숫자·코드).
- 색은 `:root` 토큰이다. 다크 모드는 `prefers-color-scheme`과 `data-theme`(`?theme=dark`) 둘 다 지원한다.
- `cur` 주황(왼쪽 카드 쪽), `wrk` 파랑(오른쪽 카드 쪽), `retry` 노랑, `bad` 빨강, `ok` 초록, `ink3` 회색 점.
- 종류마다 주황/파랑이 뜻하는 것이 다르다(`types/`). 같은 화면 안에서는 뜻을 바꾸지 않는다.

## 6. 모델

- 처리량은 실측 처리 시간에 맞춘다. 예: 32,000건 / 453.788초 ≈ 초당 70.5건.
- 칸 기반 이산 사건 스케줄러로 작업마다 시작·끝·결과(ok / cut / dup)를 미리 계산한다. 그림은 시각 t에서 그 결과를 보여 준다.
- 점 1개 = N건(예: 200건). 다른 종류의 점은 따로 정한다(예: 재시도 점 1개 = 5건). 범례에 둘 다 적는다.
- 구현 전 구조의 수치는 README에 "구현 전 모델 예상"이라고 적는다.

## 7. 삽입 모드 (블로그용)

- `?embed&s=<상황>`: 제목과 탭을 숨기고 그 상황만 보여 준다. 설명 영역은 숨기지 않는다. 최대 폭은 600px이다.
- 화면에 보일 때만 재생한다(IntersectionObserver, threshold 0.2). 처음 보일 때 t=0부터 시작한다.
- iframe 높이는 `check.js` 결과의 "iframe 높이" 표(블로그 본문 폭 720)를 쓴다.
- 페이지를 고친 뒤에는 iframe 주소에 `&v=숫자`를 올려 캐시를 피한다(GitHub Pages 캐시 약 10분).
- 티스토리 삽입 예: `<iframe src="…?embed&s=retry&v=2" width="100%" height="높이" frameborder="0" scrolling="auto"></iframe>`

## 8. 검사 (`scripts/check.js`)

`node scripts/check.js <index.html> <출력 폴더>`. Playwright와 `/opt/pw-browsers`의 chromium을 쓴다. 페이지의 `__sim.type`으로 뼈대를 알아보고 맞는 검사를 돌린다. 단계형 검사 항목은 `step.md`에 있다.

시간형에서 스크립트가 보는 것:
- 삽입 600·720, 일반 720·900·1280에서 가로 스크롤 없음, 16:10 이내
- 상황 × 단계 × 폭(삽입 600·720, 일반 720·900·1280)에서 카드 넘침 없음
- 카드마다 단계 3개, 단계마다 근거(`src`)
- 단계 클릭과 Enter로 그 시각 이동, 재생 유지, 두 카드 모두 강조
- CONFIG 좌표 기준 선·상자·이름 겹침, 패널 밖
- 실제로 그린 글자끼리 겹침, 글자가 상자 테두리에 걸침, 영역 밖(시각 0·200·380·480초와 단계 시각)
- pageerror 0개
- 상황별 iframe 높이(삽입 모드, 폭 720)
- 스크린샷: 상황 × 단계(900 일반, 720 삽입), 다크 1장

사람이 직접 볼 것: `shots/` 스크린샷(움직이는 중의 겹침, 이름, 흐름), 글 내용이 코드·실측과 맞는지, 사파리.

## 9. 시간형 CONFIG 형식

`templates/index-time.html`의 `CONFIG START`~`CONFIG END` 사이에 쓴다. 예시로 개선 비교(#192) 두 상황이 들어 있다.

```js
const CONFIG = {
  title: '화면 제목',
  kind: 'compare',               // map | flow | risk | compare → 카드 머리띠 기본값이 정해진다
  badge: null,                   // risk: {panel: 1, text: '예측 · 실측 전'}
  speed: 24,                     // 실제 1초에 모델 몇 초
  move: 7,                       // 상자 사이 이동에 걸리는 모델 시간
  axis: {unit: 'sec', tick: 60, fmt: t => '08:00', clock: t => '08:00:00'},
                                 // 순서만 있으면 {unit: 'order'} + 상황마다 ticks
  scenes: [{
    id: 'retry', tab: '재시도 지연', end: 500,
    legend: [['ink3', '점 1개 = 발송 작업 200건'], ['retry', '점 1개 = 재시도 작업 5건']],
    ticks: [{t: 0, label: '요청'}, ...],          // axis.unit이 'order'일 때만
    build: () => ({info, panels: [패널, 패널]}),  // 패널 1개면 한 장 그림
    steps: info => [t1, t2, t3],                  // 카드 단계 ①②③의 시각
    timeline: info => ({rows, marks, waits, labels}),
    cards: {L: {head, steps: [{body, ex, src: '파일:줄'} × 3]}, R: {...}}   // src는 화면에 안 나오는 근거
  }]
};
```

패널:
```js
{ name: '현재 구조', color: 'cur',
  boxes: [
    {id: 'q', type: 'pool', x, y, w, h, grid: {cols, dx, dy, ox, oy},     // 대기 상자: 점이 격자로 쌓임
     label: t => '이름', count: c => (c.n('q') * 200).toLocaleString() + '건 남음'},
    {id: 'srv', type: 'slots', x, y, w, h, slots: {n: 20, cols: 4, size: 20, gap: 7},  // 칸: 진행 링
     label: () => '서버 · 보내는 중 (20칸)', cover: t => t >= 180 ? {text: '서버 재시작', sub: ''} : null},
    {id: 'push', type: 'sink', x, y, w, h, labelAlign: 'center',          // 받는 곳: 들어가며 흐려짐
     count: c => (c.arrived('push') * 200).toLocaleString() + '건 보냄'}],
  edges: [{from: 'q', to: 'srv', pts: [[158, 92], [190, 92]]}],           // 점은 이 경로를 따라 이동
  tokens: [{id, tag, color: 'ink3', r: 3, hops: [
    {box: 'q', t: 0},                          // 처음 있는 곳
    {box: 'srv', t: 12.5, slot: 3, until: 63}, // t에 떠나 이동, until까지 진행 링
    {box: 'q', t: 63, cut: true},              // 끊김: ✕를 남기고 돌아감
    {box: 'push', t: 120, color: 'retry'}]}],  // 색 바꾸기
  notes:  [{from, to, x, y, text: t => '재시도까지 3초', align, color}],
  blocks: [{from, to, x, y1, y2, text: '못 들어감', tx, ty, align}],
  status: t => ['상태 문구', 'bad' | 'ok' | 'neu'] }
```

시간표:
```js
{ rows:   [{panel: 0, label: '발송', box: 'srv', filter: tk => tk.tag === 'f', color}],
  marks:  [{t, label: '재시도할 시각 08:05', color: 'retry'}],
  waits:  [{row: 1, a, b, text}],          // text 없으면 "N초 기다림" / "N초 뒤 시작"
  labels: [{row: 1, t, text: '모두 보냄', tone: 'ok'}] }
```

테스트 훅 `window.__sim`: `set(t)`, `play()`, `scene(id)`, `t`, `end`, `steps`, `scenes`, `kind`, `info()`, `panels`, `cards`, `playing`, `layout(t)`(그린 글자·상자 위치).
