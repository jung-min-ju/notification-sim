# ① 구조 지도

서버, 모듈, DB, 외부 서비스가 어떻게 연결되는지 보여 준다. 정적인 지도는 만들지 않는다. 요청 점이 시스템을 한 바퀴 돈다.

## 언제

- "전체 구조가 어떻게 생겼어", "이 서비스에 뭐가 붙어 있어"
- 새로 온 사람에게 구조를 설명할 때. ②의 앞 단계로 쓴다.

## 근거

- 패키지 구조, `@Controller`·`@Scheduled`·`@KafkaListener` 같은 진입점, 설정 파일, 인프라 파일(docker-compose, Terraform, k8s)
- 상자마다 근거 `파일:줄`을 명세에 적는다. 근거가 없는 상자는 넣지 않는다.

## 화면

- **패널 1개**(800 폭). 상자 위치는 모든 탭에서 같다.
- **탭 = 진입점**. 예: 사용자 요청, 스케줄러, 워커, 외부 콜백.
- 점 하나 = 요청(또는 실행) 하나. 지나가지 않는 상자와 선은 흐리게 둔다(`dim: true`).
- 상자 종류: 우리 코드(서비스, 워커)는 `slots` 또는 `pool`, 저장소(MySQL, Redis, Kafka, S3)는 `pool`, 외부 서비스는 `sink`.
- 상자 아래 숫자는 "지나간 요청 3" 같은 누적 수 하나다.
- 시간 축: 순서만(`axis.unit: 'order'`). 상황마다 `ticks`로 진입 → 서버 → 저장 → 외부를 둔다.
- 시간표 줄: 진입 / 서버 / 저장 / 외부.

## 설명 카드

- 기본 머리띠: 왼쪽 **요청이 지나가는 곳** / 오른쪽 **데이터가 남는 곳** (2026-11-19).
  - 왼쪽: 무엇이 실행됐는지. 컨트롤러 → 서비스 → 외부 호출.
  - 오른쪽: 같은 단계에서 무엇이 남았는지. 테이블 행, 캐시 키, 토픽 메시지, 파일.
- 이름이 맞지 않는 탭에서만 바꾼다. 예: 스케줄러 탭(요청이 들어오지 않음), 조회만 해서 남는 데이터가 없는 탭. 바꿀 때는 명세에 이유를 한 줄 적는다.
- 코드 상자: 진입점 메서드, 저장 호출, 외부 호출 줄.

## README에 더 적을 것

- 진입점 목록: 진입점 | 근거 `파일:줄` | 지나가는 상자 순서

## 추가 검사

- 상자마다 명세에 근거 `파일:줄`이 있는지(명세 확인)
- 탭마다 점이 지나가는 상자와 흐린 상자가 명세와 같은지(스크린샷)
