# ① 구조 지도

서버, 모듈, DB, 외부 서비스가 어떻게 연결되는지 보여 준다. 정적인 지도는 만들지 않는다. 요청 점이 시스템을 한 바퀴 돈다.

## 언제

- "전체 구조가 어떻게 생겼어", "이 서비스에 뭐가 붙어 있어"
- 새로 온 사람에게 구조를 설명할 때. ②의 앞 단계로 쓴다.

## 근거

- 패키지 구조, `@Controller`·`@Scheduled`·`@KafkaListener` 같은 진입점, 설정 파일, 인프라 파일(docker-compose, Terraform, k8s)
- 상자마다 근거 `파일:줄`을 명세에 적는다. 근거가 없는 상자는 넣지 않는다.

## 화면 (기본: 단계형 `index-step.html`, 규칙은 `step.md`)

- **상황 = 진입점**. 예: 사용자 요청, 스케줄러, 워커, 외부 콜백. 구성요소 위치는 모든 상황에서 같다. 쓰지 않는 구성요소는 흐리게 둔다(`active`에 넣지 않음).
- 구성요소 종류: 우리 코드(컨트롤러를 가진 서버, 워커)는 `box`, 저장소(MySQL 테이블, Redis, Kafka 토픽, S3)는 `db`, 사용자 기기는 `client`, 외부 서비스는 `ext`.
- 요청 하나가 진입점에서 출발해 메시지로 한 바퀴 돈다. 단계마다 메시지 1~4개.
- **요청이 지나가는 곳 / 데이터가 남는 곳**(2026-11-19 정한 두 관점)은 이렇게 나눠 보여 준다.
  - 요청이 지나가는 곳: 메시지와 `box` 강조. 지금 하는 일 글머리에 "무엇이 실행됐는지"를 쓴다.
  - 데이터가 남는 곳: `db`의 값 줄. 메시지가 도착하면 그 단계에서 남은 것(행, 캐시 키, 토픽 메시지, 파일)으로 바뀐다.
- 근거(`src`)로 자주 쓰는 곳: 진입점 메서드, 저장 호출, 외부 호출 줄.

시간형으로 만들 때(요청이 몰리는 양이 요점일 때)는 패널 1개, 시간 축은 순서만(`axis.unit: 'order'`, ticks: 진입 → 서버 → 저장 → 외부)으로 쓴다. 설명 카드 머리띠는 왼쪽 **요청이 지나가는 곳** / 오른쪽 **데이터가 남는 곳**으로 한다. 이름이 맞지 않는 탭(스케줄러 탭, 조회만 하는 탭)에서만 바꾸고 명세에 이유를 적는다.

## README에 더 적을 것

- 진입점 목록: 진입점 | 근거 `파일:줄` | 지나가는 상자 순서

## 추가 검사

- 상자마다 명세에 근거 `파일:줄`이 있는지(명세 확인)
- 상황마다 강조되는 구성요소와 흐린 구성요소가 명세와 같은지(스크린샷)
