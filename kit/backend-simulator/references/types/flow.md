# ② 흐름 추적

한 기능의 요청과 데이터가 어떤 메서드, 테이블, 메시지를 지나는지 보여 준다. 두 구조를 비교하지 않는다.

예시: 다먹자 비동기 구조(2026-11-10, KTB4-5th-BE origin/dev 4b13f19a). 기능 5개(이미지 분석, 요리 추천, 구성원 변경, 임박·만료, 요리 적용).

## 언제

- "이 기능은 어디를 거쳐", "요청 안에서 끝나는 일과 나중에 하는 일이 뭐야"

## 근거

- 호출 경로(컨트롤러 → 서비스 → 저장소), 트랜잭션 경계, 발행·구독 지점, 쿼리, 토픽 이름
- 설정으로 켜고 끄는 경로가 있으면 설정 키와 기본값(`application.yml:줄`)

## 화면 (기본: 단계형 `index-step.html`, 규칙은 `step.md`)

예시: `templates/index-step.html`의 CONFIG. 알림 발송 V2(DB 워커)의 "전체 흐름"과 "워커가 응답을 오래 기다리면" 두 상황이다(KTB4-5th-BE dev `ad6550f`).

- **상황 = 기능**(또는 한 기능의 정상/문제 흐름). 구성요소 위치는 모든 상황에서 같고, 메시지가 가는 길만 다르다.
- **요청 안에서 끝나는 일 / 워커가 나중에 하는 일**은 단계 순서와 메시지 종류로 나눠 보인다.
  - 요청 안: 요청·저장(`req`) 메시지. 트랜잭션 안에서 함께 저장되는 것은 한 단계에 묶는다.
  - 나중: 신호(`sig`)나 워커 단계. 지금 하는 일 글머리에 "커밋 뒤", "08시 배치와 따로" 같은 시점을 쓴다.
- 설정으로 켜고 끄는 경로가 있으면 "○○ 경로 꺼짐(기본값) / 켜짐"을 상황 두 개로 나눈다.
- 용어(트랜잭션, 커밋 후 발행, 아웃박스, 소비자 그룹, 오프셋, 선점)는 처음 나오는 단계의 글머리에 짧게 푼다.
- 근거(`src`)로 자주 쓰는 곳: `@Transactional` 메서드, 발행 줄(`@TransactionalEventListener`), 리스너 메서드, 쿼리, 설정 기본값.

시간형으로 만들 때(처리량이나 쌓이는 양이 요점일 때)는 패널 1개, 실측이 없으면 시간 축은 순서만 쓴다. 시간표 줄은 요청 / 발행 / 처리 / 화면 / 푸시, 카드 머리띠는 왼쪽 **요청 안에서 끝나는 일** / 오른쪽 **워커가 나중에 하는 일**이다. 점 색은 주황 = 요청 안에서 저장한 기록, 파랑 = 워커가 옮기는 메시지, 초록 = 사용자에게 알리는 신호로 쓴다.

## README에 더 적을 것

- 설정 스위치: 키 | 기본값 | 근거 `application.yml:줄`
- 기능별 경로: 기능 | 요청 안 | 나중에

## 추가 검사

- 켬/끔 두 상황의 구성요소 배치가 같은지(명세 확인)
- 흐린 구성요소로 메시지가 지나가지 않는지(스크린샷)
