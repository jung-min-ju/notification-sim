# ③ 문제 예측

코드를 보고 "이 조건이면 여기서 문제가 생길 것 같다"를 보여 준다. 실측 전이므로 화면에 **`예측 · 실측 전` 이름표**를 둔다(2026-11-19).

## 언제

- "어디서 터질까", "요청이 몰리면 괜찮아?", "외부 API가 느려지면?", "서버가 재시작되면?"

## 근거는 세 단계로 나눈다

명세와 README에 섞지 않고 따로 적는다.

1. **코드 사실**: 문제가 생길 지점의 `파일:줄`과 그 코드가 하는 일. 예: "작업마다 가상 스레드를 만들고 끝날 때까지 기다린다(PushDispatchService.java:44)".
2. **가정한 조건**: 동시 요청 수, 외부 응답 지연, 데이터 양, 재시작 시각. 값마다 왜 그 값인지 한 줄(운영 로그, 비슷한 실측, 설정 기본값, 임의).
3. **예상 결과**: 모델이 계산한 결과. 예: "재시도가 150초 늦게 시작".

그리고 **확인 방법**: 이 예측을 실측하려면 무엇을, 어떤 조건에서 재야 하는지. 실측을 하면 이름표를 떼고 ④로 넘어간다. 넘어간 기록은 README에 남긴다.

## 화면

- **패널 2개**: 왼쪽 **평소**, 오른쪽 **문제 조건**. 같은 상자 배치, 같은 축, 같은 시작 시점.
- **탭 = 문제 조건**. 예: 요청 몰림, 외부 응답 지연, 발송 중 서버 재시작, 서버 2대.
- 이름표: `badge: {panel: 1, text: '예측 · 실측 전'}`. 오른쪽 구조 이름 옆에 테두리만 있는 작은 이름표로 그린다. 화면에 두는 가정 표시는 이것 하나뿐이다.
- 문제 지점은 그림으로 보여 준다: 빨간 덮개, 막힘 막대, ✕, 쌓이는 대기 상자.
- 시간 축: 초. 시간표 줄: 처리 / 대기 / 실패.

## 설명 카드

- 머리띠: 왼쪽 **평소**(주황) / 오른쪽 **문제 조건**(파랑).
- 오른쪽 카드의 ② 진행 단계에 문제 지점 코드를 띄운다.
- 숫자를 쓸 때는 모델 예상이라는 것이 이름표로 드러나므로 따로 "약", "예상"을 붙이지 않는다.

## README에 더 적을 것

- 근거 세 단계 표: 코드 사실 | 가정한 조건(값, 이유) | 예상 결과
- 확인 방법: 측정 항목, 조건, 도구
- 상태: 예측 / 실측 완료(④로 옮긴 날짜)

## 추가 검사

- 두 패널의 축과 시작 시점이 같은지
- 이름표가 하나만 있는지(스크린샷)
- 가정한 값이 화면 글에 들어가 있지 않은지(글 확인)
