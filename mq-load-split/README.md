# 부하를 나누는 방식의 차이 시뮬레이터

정시 배치에 몰리는 임박·만료 알림을 RabbitMQ 일반 큐와 Kafka 파티션이 어떻게 나누는지 움직이는 그림으로 보여 주는 시뮬레이터예요. 가상 데이터만 쓰고, 실제 브로커나 서비스에는 연결하지 않아요.

- 주소(배포 뒤): `https://jung-min-ju.github.io/notification-sim/mq-load-split/`
- 삽입 모드: `?embed&s=<상황>` (상황: `sum`, `rabbit`, `kafka`, `hot`, `repl`)
- 파일: `index.html` 한 개. 외부 라이브러리 없이 canvas로 그려요. 글꼴만 Google Fonts에서 불러와요.

## 근거 (공식 문서, 확인일 2026-11-03)

| 글의 문장 | 공식 문서 근거 | 문서 |
| --- | --- | --- |
| 알림 큐 하나는 그 큐의 리더가 처리를 주도 | 쿼럼 큐의 모든 상태 변경은 리더로 가요. 클래식 큐는 복제본이 하나뿐이고 그게 주 복제본이에요. | [Quorum Queues](https://www.rabbitmq.com/docs/quorum-queues), [Clustering Guide](https://www.rabbitmq.com/docs/clustering) (4.4) |
| 브로커를 추가해도 기존 큐가 저절로 쪼개지지 않음 | 큐는 기본적으로 한 노드에 있어요. 새 노드는 운영자가 멤버를 추가하기 전에는 쿼럼 큐 멤버를 갖지 않아요. | 같음 |
| 큐 A·B·C와 각 리더를 분산 | 큐 리더를 노드에 고르게 나누는 게 좋다고 하고, 리더 위치를 정하는 `balanced` 전략이 있어요. | 같음 |
| 같은 냉장고를 어느 큐로 보낼지 규칙 필요 | consistent hash exchange는 라우팅 키 해시로 큐를 고르고, 바인딩이 그대로면 같은 키는 같은 큐로 가요. | [consistent hash exchange README (v3.7.x)](https://github.com/rabbitmq/rabbitmq-consistent-hash-exchange/blob/v3.7.x/README.md) |
| 복제본을 늘리는 것은 작업 분할과 다름 | 멤버가 많을수록 쿼럼 큐 처리량은 대체로 낮아져요. 복제본은 리더가 실패하면 리더를 이어받는 용도예요. | [Quorum Queues](https://www.rabbitmq.com/docs/quorum-queues) |
| 토픽은 묶음, 파티션은 나눠 담는 단위 | 토픽은 여러 브로커의 "버킷"(파티션)에 나뉘어 있어요. | [Kafka Introduction](https://kafka.apache.org/intro/) (4.4) |
| 같은 소비자 그룹 안에서 파티션을 나눠 담당, 한 파티션은 한 소비자 | 파티션 하나는 구독한 소비자 그룹마다 한 번에 소비자 한 명만 읽어요. 그룹 안 소비자 수는 파티션 수보다 많을 수 없어요(1.0 문서 문구). | [Kafka Design](https://kafka.apache.org/43/design/design/), [Introduction 1.0](https://kafka.apache.org/10/getting-started/introduction/) |
| "일반" 소비자 그룹 | share group은 파티션 하나를 여러 소비자에게 줄 수 있어요. 그래서 "일반"이라는 말이 필요해요. | [Kafka Design](https://kafka.apache.org/43/design/design/) |
| 같은 냉장고 키는 한 파티션에 집중 | 같은 이벤트 키는 같은 파티션에 써요. | [Kafka Introduction](https://kafka.apache.org/intro/) |
| 브로커 추가 뒤 파티션 재배치 필요 | 새 브로커는 파티션을 자동으로 받지 않고, 파티션을 옮기기 전까지 일을 하지 않아요. | [Basic Kafka Operations](https://kafka.apache.org/42/operations/basic-kafka-operations/) (4.2) |
| 복제는 장애 대비 | 복제 단위는 파티션이고, 리더 1개와 팔로워가 있어요. 브로커가 멈추면 리더가 다른 복제본으로 넘어가고, 돌아온 브로커는 팔로워가 돼요. 복제 계수 N이면 N-1대 장애까지 견뎌요. | [Kafka Design](https://kafka.apache.org/43/design/design/), [Basic Kafka Operations](https://kafka.apache.org/42/operations/basic-kafka-operations/), [Introduction 1.0](https://kafka.apache.org/10/getting-started/introduction/) |

문서에서 확인한 단서:

- RabbitMQ 쿼럼 큐의 지속 멤버십 조정(CMR)을 켜면 새 노드에 복제본이 자동으로 늘어날 수 있어요. 늘어나는 건 복제본이고 큐가 쪼개지는 건 아니라서 글의 문장과 어긋나지 않아요.
- RabbitMQ sharding 플러그인은 논리 큐 하나를 여러 큐로 나누고, 새 노드에 샤드를 자동으로 만들어요. 글이 말하는 "일반 큐"가 아니라 이 시뮬레이터에서는 다루지 않아요. ([rabbitmq_sharding README](https://github.com/rabbitmq/rabbitmq-server/blob/master/deps/rabbitmq_sharding/README.md))
- Kafka Introduction 최신판에서는 "그룹 안 소비자 수 ≤ 파티션 수" 문구를 찾지 못해 1.0 문서를 함께 적었어요. 같은 뜻은 Design(4.3)의 "파티션 하나는 그룹 안 소비자 한 명" 문구로 확인했어요.

## 상황 표

| 상황 | 왼쪽 | 오른쪽 | 성격 |
| --- | --- | --- | --- |
| 요약 (`sum`) | 채택 안 함: RabbitMQ 큐 A·B·C + 분배 규칙 | 채택: Kafka 파티션 0·1·2 + 소비자 그룹 | 나누는 단위와 구성 주체 |
| ① RabbitMQ 큐 나누기 (`rabbit`) | 알림 큐 1개. 브로커 4 추가, 복제본 2개 추가 | 큐 A·B·C + 분배 규칙 | 규모 대응 |
| ② Kafka 파티션 나누기 (`kafka`) | 파티션 1개. 소비자 2·3 추가 | 파티션 0·1·2, 소비자 3명 | 규모 대응 |
| ③ 한쪽에 몰리면 (`hot`) | 냉장고 1 키에 몰림. 브로커 4 추가, 재배치 안 함 | 고르게 퍼진 키. 브로커 4 추가 뒤 파티션 2 재배치 | 운영 관리 |
| ④ 복제와 분할 (`repl`) | 복제만: 파티션 1개를 브로커 3대에 복사 | 분할만: 파티션 3개를 브로커 3대에 하나씩 | 장애 대비 vs 부하 나누기 |

요약 상황은 두 구조의 처리 시간이 같아요. 차이는 나누는 단위(큐 vs 파티션)와, 나누는 구성을 누가 하는지(분배 규칙·큐를 직접 vs 토픽의 파티션 수)예요.

## 시뮬레이션 가정

- 점 1개 = 알림 묶음 1개. 모든 상황에서 24개가 정시에 들어와요(0.1초부터 0.03초 간격).
- 배치는 0.9초부터 0.09초 간격으로 브로커에 보내고, 이동은 0.45초 걸려요.
- 냉장고 1~6이 차례로 돌아가며 나와요. 큐/파티션 선택은 `(냉장고 - 1) mod 3`으로 정했어요. 실제 Kafka 기본 파티셔너는 키 해시를 쓰므로 어느 냉장고가 어느 파티션에 갈지는 다를 수 있어요. 같은 키가 같은 곳으로 간다는 성질만 따랐어요.
- 이산 사건 모델(0.01초 단위): 소비자가 비면, 맡은 큐/파티션 중 리더 브로커가 살아 있고 비어 있는 곳에서 가장 먼저 들어온 점을 가져가요. 리더 브로커는 점 하나를 내주는 데 `bd`초, 소비자는 받은 점을 처리하는 데 `pc`초 써요.
  - ①: `bd` 0.75초, `pc` 0.25초. "큐 하나는 리더가 처리를 주도"를 보이려고 리더 쪽 일을 크게 잡았어요. 그래서 왼쪽은 소비자가 3명이어도 리더 1대가 병목이에요. 이 비율은 문서에 없는 가정이에요.
  - 나머지: `bd` 0.15초, `pc` 0.85초(소비자 쪽이 병목).
- ① 브로커 4 추가 4초, 복제본 추가 9초. 복제본에는 그 시점까지 쌓인 점이 복사돼요.
- ② 소비자 2·3 추가 5초.
- ③ 왼쪽은 24개 중 16개가 냉장고 1(파티션 0), 나머지 8개가 파티션 1·2에 4개씩이에요. 브로커 4 추가 6초. 오른쪽은 6.2초에 파티션 2 재배치를 시작해 7.4초에 리더가 브로커 4로 바뀌어요. 재배치 중에도 기존 리더가 계속 내줘요.
- ④ 브로커 1 다운 4초, 복귀 10초(둘 다). 왼쪽은 4~5.5초 동안 리더를 바꾸고(1.5초는 가정, 문서에 시간 없음), 5.5초부터 브로커 2가 리더예요. 브로커 1은 복귀 뒤 팔로워로 돌아와요. 오른쪽은 복제가 없어 파티션 0이 4~10초 동안 멈춰요.
- ④ "저장한 알림"은 들어온 점 수 × 그 파티션을 가진 브로커 수예요(복사본 포함 디스크 사용). 복제 트래픽(네트워크)은 리더에서 복제본으로 가는 작은 점으로 그렸어요.
- 시간표는 브로커마다 한 줄이고, 그 브로커가 리더인 큐/파티션의 점이 내주기~처리 중일 때 막대를 칠해요. 리더가 없어 못 내준 구간은 빨간 점선 상자로 표시해요.

## 화면 조작

- 재생 속도: 1×는 실제 1초에 모델 시간 0.75초가 가요(처음 1초 = 1초는 빠르다는 의견으로 2026-11-03에 낮춤). 그림 오른쪽 아래 버튼. 멈춤/재생, 0.5×·1×·2×. 그림 폭 480px 이하에서는 멈춤과 속도 버튼(누를 때마다 0.5× → 1× → 2×) 두 개만 보여요. 주소에 `&speed=2`처럼 줄 수도 있어요.
- 화면 비율: 16:10에 맞추지 않아요(2026-11-03 요청). 그림은 비율을 고정하고, 설명 카드는 내용만큼 아래로 늘어나요. 그림 폭 520px 미만에서는 두 구조를 위아래로 쌓고, 설명 카드도 한 줄로 쌓아요.
- 시간표 끌기: 시간표를 누르거나 현재 시각 선(위쪽 손잡이)을 좌우로 끌면 그 시각으로 앞뒤로 이동해요. 끄는 동안은 멈춰 있고, 놓으면 원래 재생 상태로 돌아가요. 그림을 누른 뒤 ←/→로 1초씩, Home으로 처음으로 가요.
- 설명 카드: 세 단계 모두 본문, 풀이, 자세한 설명을 보여 줘요. 지금 단계는 강조해요.
- 자세한 설명에 쓴 사실은 위 근거 표의 문서에서 가져왔어요. "복제 계수 N이면 N-1대 장애까지 견딤"·"흔한 설정은 3"은 Kafka Introduction, "돌아온 브로커는 팔로워"는 Basic Kafka Operations예요. "멤버가 늘수록 처리량이 대체로 낮아짐"은 RabbitMQ Quorum Queues 문서, "그룹 안 소비자가 바뀌면 배정을 다시 나눔"은 Kafka 소비자 그룹 리밸런스를 따랐어요.
